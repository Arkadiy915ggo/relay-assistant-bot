# Relay Assistant: Feature Roadmap

Этот vault содержит независимые спецификации для развития Telegram-бота. Каждая задача рассчитана на отдельную агентскую сессию и ссылается на конкретные исходные файлы.

## Порядок работ

| Этап | Фича | Зависимости | Результат |
| --- | --- | --- | --- |
| 1, реализовано | [[Features/01 Aliases and Address Detection]] | Нет | Любой участник чата задаёт имена бота; адресованные сообщения безопасно распознаются. |
| 2, реализовано | [[Features/02 Intent Router and User Actions]] | Фича 1 | Обращение по имени вызывает подходящее пользовательское действие. |
| 2.5, реализовано | [[Features/02.5 Pre-Feature 03 Stabilization]] | Фичи 1-2 | Terminal outcomes, честная persistence policy и стабилизация спорных intent-ов перед очками. |
| 3, реализовано в worktree | [[Features/03 Joke Points and Leaderboard]] | Завершённый этап 2.5 | Уникальная validated шутка получает очки; есть spendable balance и top-10. |
| 4, запланировано | [[Features/04 Casino Slots]] | Проверенная и отдельно зафиксированная Фича 3 | Виртуальные очки можно поставить в versioned Telegram-слоте с atomic reserve/settle/refund. |

Фичи 1, 2, стабилизация 2.5 и Feature 03 реализованы в текущем worktree. Перед Feature 04 изменения Feature 03 должны пройти полный suite и попасть в отдельный commit. Feature 04 делится на Domain/Storage, Slash Lifecycle/Recovery и Addressed Intent; intent `casino` добавляется только на третьем этапе.

## Зафиксированные продуктовые решения

- Алиасы хранятся в SQLite отдельно для каждого чата, и сейчас ими может управлять любой участник разрешённого чата. Необязательный admin-only toggle можно рассмотреть позже; он не реализован.
- Бот реагирует на `@username` и на заданные алиасы, включая зарегистрированные сокращения и варианты имени.
- Автомаршрутизация доступна только после явного обращения к боту.
- В Feature 02 автоматически разрешены: вопрос, саммари, wiki, OCR/изображение, мем, видео, транскрибация и просмотр профиля. Казино добавляется в allowlist только вместе с Feature 04.
- Служебные и меняющие настройки команды нельзя вызывать через LLM: `/alias`, `/stats`, `/compare`, `/memory`, `/memory rebuild`, `/profile correct`, `/profile forget`.
- Очки виртуальные, только внутри одного чата, без переводов, обмена, денег и отрицательного баланса.
- Уникальная лучшая шутка даёт `+10` очков. Одна исходная реплика награждается только один раз за всю историю чата.
- Legacy rows и generated YouTube/wiki/image/video/profile/status/summary text не участвуют в Feature 03; eligibility задаётся закрытым provenance allowlist.
- `/compare` никогда не начисляет очки.
- Ставка казино: `10` очков; gross payouts `0/5/50/250`, RTP `90.625%`.
- Slot mapping фиксируется как `telegram_slots_base4_v1`; jackpot только `Dice.value=64` (`seven/seven/seven`).
- Неизвестный/не committed Telegram Dice outcome считается void, stake возвращается.
- `/top`, `/stats` leader и pinned `Топ балансов` показывают текущие spendable balances, включая casino changes.
- Feature 04 поддерживает один активный процесс; multi-instance recovery не входит в v1.

## Общие инженерные ограничения

- Не читать `.env` и `data/` при реализации или тестировании.
- Все SQLite-изменения должны быть идемпотентны: `CREATE TABLE IF NOT EXISTS` и безопасные миграции в `MessageStore.init()`.
- Все изменения баланса выполняются транзакционно внутри существующего `MessageStore._write_lock`.
- Любой результат LLM считается недоверенным до валидации. Для действий допустим только закрытый allowlist; для шуток допустимы только реальные `message_id` из базы.
- Не вызывать aiogram-handler из другого handler и не синтезировать текст `/command`: общую логику выносить в обычные async-операции.
- Feature 03 сохраняет текущий общий `gpu_lock`: summary и JokeSelector используют его двумя последовательными захватами и отдельными client objects без вложенного захвата.
- Обновлять `/help`, `README.md` и `.env.example`, если фича добавляет пользовательские команды или настройки.

## Почему роутер занимает `gpu_lock`

`gpu_lock` - это очередь для задач, которые используют локальную GPU через Ollama или Whisper. Он не блокирует event loop, но при текущем `handle_as_tasks=False` handler ожидающего update задерживает обработку следующих update; уже созданные фоновые задачи при этом продолжают работать. Это осознанный компромисс ради последовательности и стабильности.

Без lock одновременно могут стартовать, например, распознавание видео, `/summary` и короткий запрос роутера. Они конкурируют за одну VRAM, могут вызвать нехватку памяти, резко замедлить друг друга или выгрузить модель во время чужой задачи. Это особенно вероятно потому, что часть текущих задач запускается в фоне.

Роутер добавляет один короткий вызов только для адресованного свободного текста. Поэтому пользователь может заметить задержку, если в очереди уже идёт тяжёлое видео или саммари. Это компромисс ради стабильности. Прямые slash-команды не проходят через роутер, а сам роутер получает небольшой JSON-промпт без истории чата; после выбора действия уже сама команда берёт нужный контекст.
