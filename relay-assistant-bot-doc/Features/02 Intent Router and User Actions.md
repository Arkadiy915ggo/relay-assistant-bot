# Feature 02: Intent Router and User Actions

## Статус

Реализовано и стабилизировано этапом [[02.5 Pre-Feature 03 Stabilization]]. Feature 03 в этом документе не реализована.

## Цель

После явного обращения к боту распознавать, хочет ли пользователь обычный ответ или выполнение пользовательского действия, и запускать безопасную внутреннюю операцию. Пример: `Реле, сделай мем из этой картинки` запускает мем для replied/текущей картинки, а `Реле, сделай саммари за 6 часов` запускает summary.

## Зависимости

Нужна завершённая [[01 Aliases and Address Detection]]. Роутер получает уже очищенный адресованный запрос и не реализует поиск имён самостоятельно.

Address detection использует принятую политику Feature 01: короткие aliases совпадают только точно, а alias с суммарной нормализованной длиной токенов от 5 символов допускает одну вставку, удаление или замену на весь alias. Для многословного alias разрешена одна опечатка всего, не по одной на каждое слово.

## Разрешённые действия

| Intent | Аргументы модели | Операция и fallback |
| --- | --- | --- |
| `question` | `period` необязателен; `query` игнорируется | Контекстный ответ на исходный очищенный запрос. |
| `summary` | `period` необязателен | Саммари чата; при отсутствии периода используется `DEFAULT_SUMMARY_PERIOD`. |
| `wiki` | Непустой `query` обязателен | Поиск Wikipedia; пустой запрос просит уточнение и не запускает поиск. |
| `image` | Аргументы игнорируются | OCR/описание replied/текущего/последнего изображения. |
| `meme` | Аргументы игнорируются | Мем из replied/текущего/последнего изображения. |
| `video` | Аргументы игнорируются | Распознавание replied/текущего/последнего видео. |
| `transcribe` | Аргументы игнорируются | Расшифровка только replied voice/audio. |
| `profile_show` | `query` может содержать имя | Reply имеет приоритет; иначе непустое имя разрешается chat-scoped без fallback на отправителя; профиль отправителя используется только без reply и query. |
| `none` | Аргументы игнорируются | Обычный контекстный ответ на исходный очищенный запрос. |

`casino` не входит в schema, prompt и allowlist этой фичи. Feature 04 добавит его только вместе с проверкой пользователя, идемпотентностью и атомарным списанием очков.

Никогда не маршрутизировать через LLM известные и неизвестные slash-команды: `/alias`, `/stats`, `/compare`, `/memory`, `/memory rebuild`, `/profile correct`, `/profile forget` и любые другие `bot_command`. Технический вопрос с shell/API-текстом остаётся обычным `question`: безопасность обеспечивается закрытой таблицей действий, а не попыткой угадать опасный текст. Нельзя использовать `eval`, динамический `getattr`, `shell=True`, синтезировать `/command` или передавать `query` как исполняемую строку.

## Контракт роутера

Создать отдельный модуль, например `intent_router.py`. Модель возвращает JSON только такой формы:

```json
{
  "action": "summary",
  "period": "24h",
  "query": null
}
```

- Допустимые `action`: `question`, `summary`, `wiki`, `image`, `meme`, `video`, `transcribe`, `profile_show`, `none`.
- Принимается только один JSON object, который полностью занимает ответ. Markdown fences, текст вокруг JSON, массивы, scalar и несколько JSON-объектов отклоняются.
- `action` обязан быть строкой из literal allowlist. `period` и `query` могут быть строкой или `null`; значения других типов отклоняются. Лишние ключи игнорируются.
- Исходный очищенный запрос обрезается до 2000 символов до отправки роутеру. Возвращённые моделью `query` длиннее 500 символов и `period` длиннее 32 символов отклоняются как schema-invalid, а не обрезаются.
- `period` валидируется существующим `parse_period`, но дополнительно ограничивается 365 днями. Валидатор обрабатывает `ValueError`, `TypeError` и `OverflowError`; невалидный явно указанный период не подменяется default незаметно.
- `query` всегда считается данными. Для `question` используется исходный очищенный запрос, а не переписанный моделью `query`.
- Невалидный JSON/schema, timeout, исключение модели, неизвестный action и `none` не запускают действие и переходят к обычному `question` с исходным запросом и default-периодом.
- Если JSON валиден, но обязательного аргумента или media/reply нет, операция не выполняется и отправляет существующую либо короткую русскую подсказку. Не нужно молча выбирать другой action.
- Ошибка transport/provider может также сломать fallback-вопрос, если оба клиента используют один сервис. После одной попытки fallback бот возвращает понятную ошибку и не повторяет запрос бесконечно.

## Допуск к роутеру

Роутер вызывается только из существующего `handle_addressed_message()` после успешного `extract_addressed_request(...)`:

1. Разрешены подтверждённый `@username`, `text_mention` с id бота или алиас текущего чата.
2. Не обрабатываются `channel_post`, сообщения ботов и пустой запрос после удаления обращения.
3. Любая entity типа `bot_command` в `entities` или `caption_entities` запрещает запуск роутера. Нельзя ограничиваться `text.startswith("/")`, потому что media caption проходит через отдельные handler-ы.
4. Пассивное сохранение текста и индексация media завершаются до роутинга.
5. Один update вызывает роутер не более одного раза и выполняет не более одного действия.

Voice/audio не маршрутизируются по собственному caption в этой фиче. `transcribe` запускается адресованным текстовым сообщением, которое является reply на voice/audio. Существующее автоматическое распознавание video note сохраняется, если адресованное действие не было выбрано.

`/stats` является намеренным исключением из общего access contract: handler не проверяет `ALLOWED_CHAT_IDS`, чтобы оператор мог узнать `chat_id`; ответ явно содержит `access_allowed`. Это исключение не распространяется на роутер, passive persistence или другие команды.

## Контракт выполнения действий

- Slash-handler и роутер вызывают одну и ту же обычную async-операцию. Handler остаётся адаптером аргументов Telegram; handler нельзя вызывать напрямую.
- `summary` и `question`, вызванные естественным обращением, исключают текущий `message_id` запроса из загружаемого контекста, чтобы не суммаризировать команду и не дублировать вопрос. Сам исходный запрос остаётся в SQLite как обычная реплика чата.
- Для media действует строгий приоритет: подходящий reply; иначе media в текущем update; иначе последнее media только при отсутствии reply и текущего media. Reply на объект другого типа не должен fallback-иться к чужому последнему media.
- Существующие `resolve_image_for_command` и `resolve_video_for_command` переиспользуются или минимально дополняются для явной поддержки текущего media. Проверки feature flags, размера, длительности и download limit обязательны.
- `profile_show`: reply выбирает участника; без reply непустой `query` разрешается только внутри текущего чата с обработкой неоднозначности; без query показывается профиль реального `from_user`. При отсутствии пользователя или неоднозначности бот просит уточнение.
- Роутер выбирает действие, но не является авторизацией. Каждая операция сохраняет собственные access checks и ограничения.

## Политика хранения результатов

Адресованный запрос уже сохранён до запуска роутера, поэтому результат нельзя повторно писать под его `(chat_id, message_id)` через текущий `INSERT OR IGNORE`.

- Исходная пользовательская реплика сохраняется без замены.
- При routed-вызове wiki, image и video сохраняют итоговый текст под реальным `message_id` первого status/response-сообщения бота. Для обычного пути это status message, который после записи редактируется результатом. При cache hit допустимо либо заранее создать status message, либо отправить результат без фразы `Saved for summaries`, записать его по полученному id и только затем добавить подтверждение сохранения через edit. Это даёт отдельную стабильную строку без synthetic id и без потери запроса. Slash-команды сохраняют текущую политику, потому что их исходный command message пассивно не записывается.
- Transcription продолжает заменять/заполнять запись исходного voice/audio через существующий `replace_existing=True`; адресованный текстовый запрос остаётся отдельной записью.
- Summary, question, profile и meme не добавляют новую контекстную запись, сохраняя текущее поведение этих команд.
- Текст интерфейса `Saved for summaries` допустим только после успешной записи результата.

Реализованная failure policy:

- wiki/image/video/YouTube generation и отправка результата отделены от context persistence;
- если полезный результат готов, а SQLite write не удался, пользователь всё равно получает результат и безопасное предупреждение без текста DB exception;
- такой исход терминален как `partial/context_persistence_failed`, а не `failed` и не `succeeded`;
- video cache write и context write учитываются отдельно; сбой cache не уничтожает результат;
- wiki без результатов имеет `succeeded/no_results` и ничего не объявляет сохранённым.

## Terminal Operation Outcomes

Общие async-операции summary/question/wiki/image/video/profile возвращают `OperationOutcome` со статусом `succeeded`, `rejected`, `partial` или `failed`, стабильной причиной и при необходимости `persisted`, `cache_hit`, `response_message_id`. Slash- и routed-wrapper пишут один structured terminal event с invocation/route/latency/provider/model metadata без сырого пользовательского query/transcript. Необработанное исключение логируется как `failed/unhandled_exception` и пробрасывается.

`meme` и `transcribe` пока остаются принятым legacy-исключением: их `None` wrapper нормализует как `succeeded/completed`; детальные early-rejection outcomes отложены до отдельной задачи.

## Surprise Meme Policy

Просьба «пошути/рассмеши» не является явным meme intent. Незапрошенный мем возможен только с вероятностью `2%`, когда роутер успешно и валидно выбрал `question`, исходный очищенный запрос явно просит шутку и изображение находится в текущем или replied-сообщении. Latest chat image для этого не используется. Invalid/fallback/`none`/`meme_not_explicit`/явный `meme` surprise path не запускают.

## Profile Sharing

Просмотр profile разрешён только при явном слове «профиль» или «паспорт»; вопросы об имени/модели/возможностях бота остаются question. Профили chat-scoped: reply выбирает автора replied-сообщения, имя ищется только среди участников текущего чата, неоднозначность просит уточнение, а fallback на отправителя при непустом имени запрещён. Любой участник разрешённого чата может использовать существующие `/profile correct` и `/profile forget` для другого участника по reply/имени; это принятая shared-chat политика.

## Почему нужен `gpu_lock`

Для Ollama роутер - ещё один запрос к локальной модели, пусть и короткий. Он обязан выполняться под существующим `gpu_lock`, как summary, вопрос, OCR, мем, видео и Whisper. Иначе несколько задач могут одновременно занять VRAM, вызвать OOM или столкнуться с выгрузкой модели после чужой задачи.

Это означает не ошибку, а очередь: если идёт тяжёлый `/video`, адресованный запрос сначала ждёт завершения видео, затем роутер быстро определяет intent, после чего действие снова занимает очередь. Прямые slash-команды не платят за этот дополнительный классификационный вызов. Роутер не получает историю чата, поэтому его запрос короткий; история загружается только для выбранной операции.

Последовательность обязательна:

1. Захватить общий `gpu_lock`.
2. Вызвать только `IntentRouter.route(...)` с timeout.
3. В `finally` выгрузить router-клиент, пока lock ещё удерживается.
4. Освободить lock.
5. Запустить выбранную операцию; она сама захватит тот же lock, если использует модель/Whisper.

Нельзя вызывать операцию внутри router-lock: `asyncio.Lock` не reentrant, и вложенный захват приведёт к deadlock. Нельзя выгружать router-модель после освобождения lock: другая задача уже может начать использовать GPU.

## Клиент и ресурсные лимиты

- Создать отдельный `LLMClient` для роутера в `main()` и инъецировать `IntentRouter` в `create_dispatcher()` для подмены fake-объектом в тестах.
- Переиспользовать текущий provider и `QUESTION_MODEL`, если он задан, иначе основную модель. Не переиспользовать сам объект `ChatAssistant` или его клиент.
- Для Ollama создать клиент с `num_ctx=2048` и `num_predict=96`. Вызов `route()` ограничить `asyncio.timeout(90)` для обоих providers.
- Новые env-переменные в этой фиче не обязательны. Если реализация всё же добавляет настройку, синхронно обновить `Settings`, `.env.example`, `/stats`, README и `doctor.py`.
- Не менять `handle_as_tasks=False` в рамках этой фичи. Отдельно логировать action, результат валидации/fallback, latency, provider/model, chat id и message id без сырого query, если content capture отключён.

## Техническая интеграция

- `src/tg_summary_bot/llm.py` уже поддерживает `response_format="json"`; протокол `LLMClient` менять не требуется.
- В `bot.py` вынести содержимое пользовательских handler-ов в callable async-операции: summary, wiki, image, meme, video, transcribe, profile show и question.
- Handler остаётся тонким адаптером Telegram-команды; роутер вызывает операцию напрямую с реальным `Message` и `Bot`.
- Вызывать роутер в общем обработчике адресованного сообщения после Feature 01, включая путь caption медиа.
- Не добавлять новый catch-all handler: текущие image/video/text handler-ы уже вызывают `handle_addressed_message()` после пассивного сохранения. Voice/audio и channel handlers сохраняют существующее поведение.
- Сохранить cache video recognition, cleanup временных файлов, Telegram splitting, response logging, profile refresh и unload всех существующих операций. Slash-команды сохраняют своё status/edit/reply поведение; routed-обёртка может создать отдельный status/response для безопасного хранения результата по правилам выше.

## Критерии готовности

- Роутер запускается только после подтверждённого `@username`, `text_mention` на id бота или настроенного алиаса текущего чата.
- Bot/channel/slash-command не запускают роутер.
- Модель не может вызвать действие вне allowlist, даже если вернёт похожий JSON.
- `Реле, сделай саммари за 6 часов` выполняет summary с периодом `6h`.
- Запрос мема с reply на фото использует именно replied-фото.
- Reply на неподходящий тип media не выбирает молча последнее media чата.
- Ошибка JSON/schema и `none` выполняют обычный contextual question с исходным запросом; provider outage завершается понятной ошибкой без side effect.
- Wiki/image/video result действительно читается из SQLite после адресованного вызова, а исходный запрос не потерян.
- Один update вызывает максимум одну классификацию и одно действие.
- Для Ollama одновременные router/summary/video не используют GPU параллельно.
- Router unload завершается до освобождения lock, а действие запускается после освобождения router-lock.
- Slash-команды работают прежним путём и не платят за классификацию.
- Missing wiki query просит уточнение и не запускает question fallback.
- Полезный generated result переживает context persistence failure с terminal `partial` и безопасным предупреждением.
- Surprise meme следует только явной 2% политике valid question + joke request + current/replied image.
- `/stats` отвечает для discovery даже вне allowlist, не разрешая остальные операции.
