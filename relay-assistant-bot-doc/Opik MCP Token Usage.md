## Короткий вывод

В локальной истории этого проекта найдено **95 вызовов Opik MCP в 6 сессиях**. Их сохранённые ответы занимают **139 995 токенов** по токенизатору `o200k_base`, аргументы — ещё **4 308**. Это объём текста, а не счёт провайдера и не расход за один запрос.

Главный источник объёма — `read`: **66,5% токенов ответов**. Типичный ответ `read` занимает около **2 тыс. токенов**, максимальный — **15,4 тыс.** Небольшие списки существенно дешевле.

- Период найденных вызовов: **4 июля — 13 октября 2026, UTC**.
- Посчитаны сохранённый `state.output` и JSON аргументов `state.input`.
- Метод: установленный в окружении проекта `tiktoken`, кодировка `o200k_base`.
- Подсчёт точный для этой кодировки и сохранённого текста, но лишь оценочный относительно фактической токенизации используемых моделей.
- Новые запросы к Opik для проверки не выполнялись. Содержимое traces в отчёт не перенесено.

## Много это или мало?

Для ориентира, относительно условного контекста в 100 000 токенов:

- Медианный `list`, 79 токенов: **мало**, около 0,08%.
- Медианный `read`, около 2 030: **умеренно**, около 2%.
- Самый большой `read`, 15 352: **много для одного результата**, около 15%.
- Самая большая загрузка skill, 5 825: **заметно**, около 6%.

100 000 — только база сравнения, а не утверждение о лимите текущей модели. Суммарные 140 тыс. распределены по нескольким сессиям и не означают, что весь этот текст одновременно находился в контексте.

**Практический вердикт:** пользоваться Opik MCP нормально. Экономить в первую очередь стоит на полном чтении больших traces, широких списках и повторной загрузке уже полученных инструкций.

## Почему это не равно оплаченным токенам

MCP возвращает данные; токены основной модели расходуются, когда OpenCode включает эти данные в LLM-запрос.

Есть несколько составляющих:

1. **Описания инструментов и JSON-схемы.** Могут добавляться к запросам даже до первого вызова. Исторические payloads с точными определениями инструментов в этой проверке не восстановлены, поэтому этот объём не измерен.
2. **Аргументы вызова.** Обычно генерируются моделью как часть tool call. Здесь измерен текст JSON, без служебной обвязки протокола.
3. **Ответ MCP.** Обычно становится входным контекстом следующих запросов модели.
4. **Повторное использование истории.** Один ответ может попадать в несколько последующих запросов, пока остаётся в истории. Кэширование меняет стоимость повторного чтения; compaction и усечение меняют сохраняемый объём.
5. **Рассуждения и итоговый ответ модели.** Не включены в таблицу и не могут быть точно приписаны MCP по одним размерам результатов.

В шести найденных сессиях счётчики сообщений показывают 13 011 378 входных токенов и отдельно 167 596 906 `cache_read`, а также 321 947 выходных и 223 378 `reasoning`. **Это общие показатели сессий со всеми задачами и инструментами, а не расход Opik.** Без проверки семантики usage каждого провайдера эти категории нельзя просто складывать. Делить 140 тыс. на общий input и называть результат долей стоимости Opik тоже некорректно: в таблице каждый ответ посчитан один раз, а история может передаваться многократно.

Денежная стоимость не рассчитана: нужны применённые тарифы, сведения о кэше и фактические запросы к провайдеру. Возможные внутренние LLM-затраты исторического `ask_ollie` здесь также не измерены.

## Обнаруженная неточность встроенных оценок

В заголовке самого большого сохранённого ответа `read` указано **7 461 tok returned**, тогда как весь сохранённый ответ даёт **15 352 токена** по `o200k_base`: примерно в **2,06 раза больше**.

Причина расхождения не установлена. Значение в заголовке сервера нельзя автоматически считать фактическим usage текущей модели. Простая эвристика «число символов / 4» для этого ответа тоже даёт лишь около 7,5 тыс. токенов и существенно занижает результат.

## Как сократить расход

1. Начинать с `list` с узким периодом `since` и фильтрами, запрашивать примерно **5–10 строк**, когда этого достаточно.
2. Выбирать необходимые `fields`. Большое поле вроде `metadata` всё равно может быть объёмным: один найденный список из 20 строк с выбранными полями занял 4 152 токена.
3. Полный `read(trace)` использовать, когда действительно нужна вся цепочка. Для локального вопроса читать нужный `span` или выбранные поля записи.
4. Не перечитывать уже полученные skills и схемы без необходимости. При этом обязательную загрузку релевантной инструкции перед работой сохранять.
5. Крупный результат разбирать сразу, фиксировать короткие выводы и избегать повторных полных чтений.

Ориентир для будущих проверок: ответ до **1 тыс. токенов** обычно компактный; **1–5 тыс.** — нормальный диагностический объём; **свыше 10 тыс.** — повод проверить, можно ли сузить запрос. Это рабочие ориентиры, а не лимиты Opik.

## Ограничения

Это аудит сохранённой локальной истории одного проекта, а не всех клиентов Opik и не гарантированно полная история использования. Точный добавочный расход и стоимость MCP требуют записи фактических LLM-payloads, usage и состояния кэша; текущие данные позволяют надёжно оценить размеры сохранённых ответов, но не восстановить полный биллинг.
